# Hospital Information System (HIS)

A secure, offline-first desktop **Hospital Information System** MVP — a single-user,
single-device clinical workflow application demonstrating software architecture, relational
database design, cross-module state synchronization, and security engineering.

**Tauri 2.x** · **React 18 + TypeScript** · **Rust** · **SQLite + SQLCipher**

> This repository is planned and governed by the documentation framework in
> [`.claude/`](.claude/README_Project.md). Start at [CLAUDE.md](CLAUDE.md) for orientation and
> [`.claude/Rules.md`](.claude/Rules.md) for the binding rules.

## Overview

The application follows the full patient-centered clinical workflow — registration, medical
history, bed assignment, operating room scheduling, inventory/pharmacy, billing simulation, and
discharge — behind a mandatory authentication gate. It is deliberately not a commercial HIS:
billing is a simulation with no real payment processor, and there is no networking,
multi-tenancy, or cloud component.

| Module               | Owns                                                                                         | Notes                                     |
| -------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Authentication       | `users`, `sessions`                                                                          | Gate for everything; first-run bootstrap. |
| Patients             | `patients`                                                                                   | Root entity of the workflow.              |
| Medical History      | `encounters`, `diagnoses`, `treatments`, `evolutions`                                        | Append-only.                              |
| Hospital Map         | _(reads `floors`, `rooms`)_                                                                  | Read-only visualization, never writes.    |
| Beds                 | `floors`, `rooms`, `beds`, `bed_assignments`                                                 | Owns facility configuration.              |
| Operating Rooms      | `operating_rooms`, `or_reservations`                                                         | Scheduling only.                          |
| Inventory            | `inventory_categories`, `inventory_items`, `inventory_transactions`, `maintenance_schedules` | Pharmacy/Lab are consumers.               |
| Notifications        | `notifications`                                                                              | Generated by other services.              |
| Audit                | `audit_log`                                                                                  | Hash-chained, append-only.                |
| Billing (Simulation) | `billing_simulations`, `billing_items`                                                       | No real payment processing.               |

## Architecture

Two OS processes form the primary security boundary — a compromised WebView cannot reach the
database or filesystem without passing through a validated, allowlisted Tauri command.

```
Presentation        React components/pages          src/modules/*/components
Application State   TanStack Query + Zustand         src/modules/*/hooks, api
══════════════════ IPC BOUNDARY (Tauri invoke/emit) ═══════════════════
Command              Tauri #[command] fns             src-tauri/src/commands
Service               Business logic / orchestration   src-tauri/src/services
Repository            Data access (SQL only)           src-tauri/src/repositories
Database              SQLite + SQLCipher                src-tauri/migrations, db/
```

- **Core process (Rust)** owns the SQLCipher connection, business logic, filesystem/OS access,
  session state, and the encryption key.
- **WebView process (React/TS)** renders UI only, talking to the core exclusively through
  `invoke` (request/response) and `listen`/`emit` (events).
- Cross-module communication happens through exactly two channels: the database as the single
  source of truth, and Tauri events (`<module>:<entity>:<action>`) for real-time propagation.

Full architectural decision record: [`.claude/Architecture.md`](.claude/Architecture.md).

## Security

- Passwords hashed with **Argon2id**; the SQLite database is encrypted at rest with
  **SQLCipher (AES-256)**.
- The database encryption key is generated once and stored in the OS keychain via the
  `keyring` crate — never written to disk in plaintext.
- Every authenticated user sees the same application; auth exists for audit, traceability, and
  access protection rather than role-gated UI.
- Every input crossing the IPC boundary is validated twice: Zod client-side for UX, the Rust
  `validator` crate server-side as the authoritative check.
- Clinical records (`encounters`, `diagnoses`, `treatments`, `evolutions`) are append-only; a
  correction is a new row referencing the row it corrects.
- The `audit_log` table is hash-chained and trigger-enforced append-only.

Full detail: [`.claude/Security.md`](.claude/Security.md).

## Prerequisites

- Node.js LTS (20 or newer)
- Rust stable toolchain (`rustup`)
- Platform Tauri prerequisites — WebView2 on Windows, `libwebkit2gtk-4.1-dev` and friends on
  Linux. See the [Tauri prerequisites guide](https://tauri.app/start/prerequisites/).

## Getting started

```bash
npm install
npm run tauri dev
```

On first run, the app has no users — you will be guided through a one-time bootstrap flow that
creates the initial administrator account.

### Seeding local test data

For local development and manual testing, a dev-only Rust binary seeds realistic fictitious
data (users, patients, floors/rooms/beds, encounters, inventory, and more) directly into the
encrypted database, reusing the same connection, hashing, and migration logic as the real app.
It is never referenced by `main.rs` or the Tauri command registry, so it cannot ship or run in
production:

```bash
cd src-tauri
cargo run --bin dev_seed -- "<path-to-health.db>"
```

On Windows, the database lives at `%APPDATA%\com.healthproject.his\health.db`.

## Quality gates

CI runs the gates in the fixed order defined by
[`.claude/Testing.md`](.claude/Testing.md) Section 7. Coverage thresholds are enforced: 80% for
Rust services/repositories, 80% for TypeScript business logic, 70% for React components. A
pre-commit hook (`husky` + `lint-staged`) runs Prettier and ESLint on staged TypeScript, plus
`cargo fmt`/`clippy` when Rust files are staged. Hooks are never bypassed with `--no-verify`.
